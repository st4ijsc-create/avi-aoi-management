# RuSTy 1.0.7 phình bộ nhớ khi biên dịch `CASE` có nhãn trùng giữa các nhánh — ca tối thiểu + bản báo upstream

Ngày đo: 2026-10-22 · Người đo: kiem-dinh · Chưa gửi ra ngoài (chờ chủ dự án duyệt).
Nguồn ca lớn: `server/services/flow/lib/__fixtures__/rusty-no-bo-nho-ud3.st` (do-model, commit 06c0c2760; 154 dòng, 2 khối chức năng).

## 1. Kết luận

- **Nguyên nhân gốc**: front-end của `plc` (RuSTy 1.0.7) CHỈ báo `E078 Duplicate condition value` khi hai nhánh `CASE` đều là nhãn ĐƠN trùng nhau (`3:` … `3:`). Khi nhãn nằm trong DANH SÁCH (`1, 2:`) và trùng với nhãn của nhánh khác, kiểm tra ngữ nghĩa bỏ qua; IR sinh ra có `switch` với `case` trùng. Ở chế độ `--ir` bộ dựng LLVM bắt được ("duplicate case value in switch", rc 1, tức thời). Ở chế độ `-c` (sinh mã đối tượng) tiến trình KHÔNG dừng mà phình bộ nhớ không giới hạn cho tới khi bị cgroup giết (rc 137, `OOMKilled=true`).
- **Ca tối thiểu 11 dòng** (xem §3). Ba dạng kích hoạt, đã đo: (a) hai nhánh cùng danh sách `1, 2:` / `1, 2:`; (b) hai nhánh chung ≥ 2 nhãn (`1, 2:` / `2, 1:`); (c) một nhãn xuất hiện ở ≥ 3 nhánh (`1, 9:` / `2, 9:` / `3, 9:`). KHÔNG kích hoạt: chung đúng MỘT nhãn giữa hai nhánh (`1, 2:` / `2, 3:`), nhãn trùng bên trong một nhánh (`1, 1:`), khoảng (`1..3:` / `2:`), thân rỗng.
- Ca lớn của do-model nổ vì khối `CASE CurrentState OF 1,2,3,4,5: … 2,3,4: … 3: …` (nhãn 3 ở ba nhánh, 2 và 4 ở hai nhánh); bỏ nhánh `2, 3, 4:` hoặc nhánh `1, 2, 3, 4, 5:` (còn nhãn 3 ở hai nhánh) hoặc đổi nhãn thành rời nhau thì biên dịch xong tức thì (đã đo; riêng việc bỏ nhánh `3:` chưa đo).

## 2. Môi trường và lệnh tái hiện

- Ảnh `st-rusty:1.0.7` (ID `2bb0a9d6ae43`; `plc --version` → `1.0.7`), Docker 29.8.2 / Docker Desktop, VM 24 CPU, 31,2 GiB RAM, Windows 11.
- Lệnh tối thiểu (không prelude, không thư viện chuẩn, không cờ lạ):

## 3. Ca tối thiểu (`min.st`)

```
PROGRAM P
VAR
    S : INT;
    X : INT;
END_VAR
    CASE S OF
        1, 2:
            X := 1;
        1, 2:
            X := 2;
    END_CASE
END_PROGRAM
```

## 4. Số đo (docker, ca tối thiểu, chạy một mình, `-c`)

| `--memory` (= `--memory-swap`) | thời gian đến khi bị giết | `OOMKilled` | mẫu `docker stats` (MemUsage) |
|---|---|---|---|
| 512m | ~2,3 s | true | 0 B |
| 2g | ~4,3 s | true | 661 MiB → 0 B |
| 6g | ~10,1 s | true | 659 MiB → 2,56 GiB → 2,60 GiB → **5,64 GiB** → 0 B |

Bộ nhớ tăng đơn điệu cho tới trần cgroup bất kể trần là bao nhiêu (thời gian tỷ lệ với trần ⇒ không có điểm dừng). Ca 154 dòng của do-model: rc 137 sau ~11 s ở 6g khi chạy một mình (trước đó test của do-model ghi ~1 s ở trần nhỏ hơn). Chạy 5 ca song song làm thời gian kéo dài (10–55 s) nhưng kết quả không đổi.

Quá trình thu nhỏ (delta-debug, ~35 lần chạy): 154 dòng → tách hai khối (khối gọi `ChotLoi` một mình biên dịch tốt; khối `BangTaiTuanTu` thiếu `ChotLoi` báo E052) → bỏ máy trạng thái, giữ riêng khối `CASE` cuối → thu `1,2,3,4,5 / 2,3,4 / 3` → `2,3 / 3,4 / 3` → `1, 2 / 1, 2` (11 dòng).

## 5. Tác động tới sản phẩm và việc nên làm phía ta (không đợi upstream)

- Mã do model sinh ra có thể chứa nhãn `CASE` trùng (đã xảy ra: bài ud3) ⇒ làm container biên dịch bị OOM-kill; `bienDichST.ts` đã phân loại 137 sớm là `ha-tang` (đúng), nhưng mô hình KHÔNG nhận được chẩn đoán hữu ích để tự sửa.
- Đề xuất: trước khi gọi `plc -c`, chạy `plc <tệp> --ir --check`? KHÔNG bắt được (rc 0). Cách bắt được: chạy `plc --ir -o` (rc 1 tức thì, thông điệp "duplicate case value") làm bước thử rẻ trước `-c`; hoặc một bước kiểm tra nhãn CASE trùng bằng phân tích văn bản/AST phía Node, báo cho model "nhãn N xuất hiện ở nhiều nhánh CASE". Việc này thuộc do-model (bienDichST.ts) — chỉ đề xuất.

## 6. Bản báo upstream (tiếng Anh, chưa gửi)

**Title**: `plc -c` allocates memory without bound (OOM) when two CASE branches share ≥ 2 labels or one label appears in ≥ 3 branches; `--ir` reports "duplicate case value in switch"

**Version**: RuSTy `plc 1.0.7` (Docker image built from the 1.0.7 release), Linux x86_64 container, Docker 29.8.2.

**Summary**: A `CASE` statement in which labels are duplicated across branches (written as comma-separated lists) passes semantic validation. Generating IR with `--ir` fails fast with an LLVM builder error, but generating an object file with `-c` never terminates and its memory use grows monotonically until the process is killed by the container cgroup (exit 137, `OOMKilled=true`). Plain duplicates written as single labels (`3:` … `3:`) are correctly rejected with `E078 Duplicate condition value`, so the check seems to cover only single-label branches.

**Reproducer** (`min.st`):

```
PROGRAM P
VAR
    S : INT;
    X : INT;
END_VAR
    CASE S OF
        1, 2:
            X := 1;
        1, 2:
            X := 2;
    END_CASE
END_PROGRAM
```

**Commands / observed**:

```
plc min.st --ir --check          # rc 0, no diagnostics
plc min.st --ir -o m.ll          # rc 1: error: Builder error: …: duplicate case value in switch   (immediate)
plc min.st -c -o m.o             # never finishes; memory grows until killed (rc 137)
```

With `--memory 512m / 2g / 6g` the process was OOM-killed after ≈ 2.3 s / 4.3 s / 10.1 s; `docker stats` showed ≈ 0.66 GiB, 2.6 GiB, 5.6 GiB successively at 6g, i.e. no plateau. Adding `-O none` does not help.

**Triggers** (all reproduce): `1,2:` / `1,2:` · `1,2:` / `2,1:` · `1,9:` / `2,9:` / `3,9:` · `2,3:` / `3,4:` / `3:`.
**Not triggering**: `1,2:` / `2,3:` (one shared label between two branches), `1,1:` (duplicate inside one branch), `1..3:` / `2:`, empty branch bodies.

**Expected**: the semantic validator reports `E078 Duplicate condition value` for every label that appears in more than one branch (as it already does for single-label branches), and/or `-c` fails like `--ir` does when the generated module is invalid, instead of consuming unbounded memory.

**Workaround**: reject/deduplicate CASE labels before compilation, or run `plc --ir` first as a cheap validity probe.
