# WS-F1 — Packaging: Installer + Windows Service — Blueprint (code-grounded)

> Turn "copy a folder + double-click" into a real installable product: a Windows Service host + a WiX MSI. Toolchain-split like WS-A's Tauri (buildable core now; installer build-if-WiX-else-documented). 4 TDD tasks, subagent-driven.

## Toolchain reality
Confirmed absent: WiX (wix/candle/light), MSIX makeappx, signtool. BUT WiX v4 is a small NuGet-hosted **dotnet global tool** (`dotnet tool install --global wix`) — materially different from Tauri's multi-GB Rust+MSVC. → Attempt the install FOR REAL in the installer task; if it succeeds, build the MSI; if network/egress fails, commit the same WiX project as a documented-not-built recipe (README §13.4 Tauri style). Windows Service = pure `Microsoft.Extensions.Hosting.WindowsServices` (ordinary NuGet, zero toolchain risk) — fully buildable+testable now.

## Decisive facts (verified)
- **St4i.EngineApi IS the service** (NOT EdgeService): it's the only composition root with historian (Program.cs:296-319), WAL (206-259), auth/RBAC/audit/security-dir-ACL (62-188). Program.cs:99-108's OWN comment says "meant to eventually run as a Windows Service (WS-F1)" and set DPAPI LocalMachine scope for exactly this. EdgeService is a 27-line bare-pipeline proof that hardcodes `new DemoTransport()` (EdgeWorker.cs:70), no historian/auth — do NOT duplicate ~300 lines into it.
- `AddWindowsService()` (on WebApplicationBuilder.Services) is SELF-GATING via `WindowsServiceHelpers.IsWindowsService()` (parent=services.exe, SessionId==0) → no-op when run interactively or as DesktopShell's spawned child. Safe alongside both.
- Port/config for a service: services don't inherit user env; set per-service registry `HKLM\SYSTEM\CurrentControlSet\Services\St4iEngineApi\Environment` (REG_MULTI_SZ) for ASPNETCORE_URLS / ST4I_HISTORIAN_DIR / ST4I_WAL_DIR / ST4I_SECURITY_DIR / ST4I_DEMO_ENABLED. Document.
- **Service account = LocalSystem**: `SecurityDirAcl.Apply` (SecurityDirAcl.cs:46-92) grants FullControl to SYSTEM + Administrators + the dir's creator-owner ONLY; SYSTEM is unconditionally granted → LocalSystem always works regardless of which account first created %ProgramData%\ST4I\sim\*. A custom low-priv account only works if it created the dirs first (fragile across migrate/reinstall). LocalSystem = highest priv (document trade-off; hardened dedicated-account = documented-not-default).
- **DesktopShell coexistence already correct**: MainWindow.xaml.cs:90-130 probes /v1/health → ATTACHES if the service already answers :5199 (never spawns a 2nd), and Closing (298-311) kills only `_ownedEngineProcess` (null on attach) → never kills the service. No new work; just "don't also run a manual EngineApi on :5199".
- **No <Version> anywhere** (no csproj Version, no Directory.Build.props) → WiX MajorUpgrade needs one. Foundation: add Directory.Build.props <Version>1.0.0</Version> + a fixed UpgradeCode GUID (never regenerate).

## FAST-FOLLOW gaps surfaced (NOT WS-F1 scope — flag for after):
- (a) FleetHost settings (serverUrl/machineCode/verifyTls) are IN-MEMORY ONLY (FleetHost.cs:142-145,883-903), reset on restart — a headless service has no browser to re-Connect after each restart unless env-configured or Settings persisted to disk. 
- (b) `CredentialStore` uses DataProtectionScope.CurrentUser → a desktop-onboarded mk_ can't be decrypted after converting to a service under a different account (re-claim needed). One-line fix to LocalMachine, same rationale as the key ring — fast-follow.
