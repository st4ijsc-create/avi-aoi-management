# AOI/AVI Config-Exchange Standards — Research Report

Deep-research (25 sources fetched, 105 claims extracted, 25 adversarially verified: 23 confirmed / 2 killed). Confidence is **high for IPC-CFX and OPC UA Machine Vision** (many independently re-verified claims against primary standard sources); **medium for IPC-2581/DPMX, MTConnect, and drift-governance best practices** (fewer claims survived the verification budget). Compiled 2026-07-20 for the ST4I simulator config-sync feature.

## Bottom line
**No industry standard defines an interoperable, structured schema for AOI measurement-point definitions + spec limits + reference images.** Every standard treats inspection-recipe *content* as an opaque vendor blob and standardizes only the **transport/management** around it (transfer, activate, version-tag, change-notify). The practical implication: designing our own rich internal config schema (measurement points + full spec + images, versioned, 2-way, governed) is the correct approach — there is no standard schema to adopt. Where we should align is on the **envelope**: identity/versioning/audit semantics, which the standards do define and which we can mirror for future interoperability.

## 1. Which standards carry measurement points / spec limits / recipes / images?

### IPC-CFX (IPC-2591) — the SMT-relevant one; bidirectional; opaque recipe blob + partial structured inspection schema
- CFX is **omnidirectional** (fully bidirectional, not pull-only): AMQP 1.0 publish/subscribe + request/response; "any CFX endpoint connection can consume data as well as create it." [electronics.org/ipc-2591-connected-factory-exchange-cfx; connectedfactoryexchange.com AmqpCFXEndpoint]
- **Remote Recipe Management** messages (CFX.Production namespace): `UpdateRecipeRequest` (host/MES→machine push; `Overwrite` replaces the same-named recipe), `GetRecipeRequest`/`GetRecipeResponse` (pull), `ActivateRecipeRequest`/`ActivateRecipeResponse` (activate a named recipe at the endpoint), `GetActiveRecipeRequest`, and `RecipeModified` (machine→MES change notification). Push + pull coexist → genuinely bidirectional. [connectedfactoryexchange.com/html/N_CFX_Production.htm, T_CFX_Production_UpdateRecipeRequest.htm, T_CFX_Production_ActivateRecipeResponse.htm, T_CFX_Production_RecipeModified.htm]
- **CFX.Structures.Recipe** has exactly 10 flat fields: `Name`, `Revision` (single OPTIONAL free-text string, e.g. "2.0"/"C" — **not** a revision graph/lineage/history), `RecipeData` (`byte[]`, "a binary representation of the recipe data" — base64 in the JSON-over-AMQP wire, carried in-band or out-of-band), `MimeType` (can be `application/octet-stream` **or a CFX-specialized type such as IPC-2581/DPMX**), plus `ExpectedCycleTime`/`ExpectedWorkTime`/`ExpectedUnitsPerWorkTransaction`/`UnitLength`/`UnitWidth`/`UnitHeight`. So the *base* recipe content is an opaque MimeType-tagged blob. [connectedfactoryexchange.com T_CFX_Structures_Recipe.htm; github IPCConnectedFactoryExchange/CFX]
- **However**, CFX v1.3+ DOES define *structured* inspection-recipe subclasses that inherit from Recipe: `SolderPasteInspectionRecipe` (fields `Fiducials`, `InspectionMethod`, `UnitsToInspect` = "the static recipe information for each Unit to be inspected"), `PCBInspectionRecipe` ("a dynamic recipe structure for AOI equipment" with Board/Component sub-structures), and `InspectionMeasurementTarget` (holds the static per-measurement target/spec values "already transferred within the Recipe", vs `InspectionMeasurementLean` = dynamic results). So for SPI/AOI, CFX models *some* structured measurement targets — the closest any standard gets. [connectedfactoryexchange.com T_CFX_Structures_SolderPasteInspection_*]
- CFX **result** messages (`UnitsInspected` → `InspectedUnit` → `Inspection` → `Measurement`/`NumericMeasurement.MeasuredValue: NumericValue`) carry per-reading `ExpectedValue`, `MinimumAcceptableValue`, `MaximumAcceptableValue` (+units) and `ToleranceMin`/`ToleranceMax` (on `ComponentVisionTest`/`ComponentElectricalTest`), plus base64 **defect** images — i.e., spec limits travel *with results* (machine→MES), and only defect (not golden/reference) images are carried. [connectedfactoryexchange.com T_CFX_Structures_NumericValue.htm, ComponentVisionTest]

### OPC UA for Machine Vision (OPC 40100-1, v1.00, 2018/2019) — the vision-specific companion spec; bidirectional; opaque black-box recipe
- Full title: "OPC UA for Machine Vision — Part 1: **Control, configuration management, recipe management, result management**." Scope explicitly covers surface inspection, assembly checks, pass/fail quality, gauging → the AOI/AVI domain. It is the only OPC UA companion spec for optical inspection. [reference.opcfoundation.org/specs/OPC-40100-1]
- Recipe transfer is **bidirectional** via `RecipeTransferType` (subtype of `TemporaryFileTransferType`, §7.6.2): `GenerateFileForRead` (export a recipe OUT of the vision system → machine→client "upload") and `GenerateFileForWrite` (import a recipe INTO the vision system → client→machine "download"). `RecipeManagementType` (§7.5.2) defines `AddRecipe`/`PrepareRecipe`/`UnprepareRecipe`/`GetRecipeListFiltered`/`RemoveRecipe`. [reference.opcfoundation.org/MachineVision/v100/docs/7.6, /7.5.2]
- Recipe **content is an opaque binary black box**: "Recipes are handled as binary objects"; "the internal composition and interpretation of recipes … is outside the scope of this specification." Identity via `RecipeIdExternalDataType` (client-supplied) and `RecipeIdInternalDataType` (system-assigned; **InternalId may be a hash for binary identity**). **No** typed nodes for measurement points, tolerances, or reference images — deliberately vendor-extensible. Part 2 (2024) adds only Asset Management/Condition Monitoring. [reference.opcfoundation.org/MachineVision/v100/docs/B.1, /12.9, /12.10]

### IPC-HERMES-9852 — not a config channel
- Horizontal board-to-board **M2M handover** along the SMT line (the SMEMA-connector successor); carries board/product ID for the handoff handshake, **not** recipe/spec/config. Explicitly **complementary** to CFX ("Hermes = horizontal, CFX = vertical to MES"). v1.4 added alignment with IPC-2591 (CFX) and IPC-2581. [the-hermes-standard.info/q-a; electronics.org IPC-CFX-and-Hermes]

### SECS/GEM + SEMI E139 (RaP) / E42 — semiconductor, not SMT/AOI
- **SEMI E139** "Recipe and Parameter Management (RaP)": specifies "cooperative interaction between the factory information and control system (FICS, includes MES) and the equipment to manage the specifications of equipment processing (e.g. equipment recipes)." Subordinate specs: E139.1 (XML Schema for the PDE = Process Definition Element), E139.2 (SECS-II protocol), E139.3 (XML/SOAP binding). SEMI E42 is the older Recipe Management Standard. **These are semiconductor-fab standards (SECS/GEM world), not adopted in SMT/electronics AOI.** (E139-0613 currently listed "Inactive".) [store-us.semi.org E13900, E04200; cimetrix RaP]

### IPC-2581 / DPMX and MTConnect (medium confidence — fewer verified claims)
- **IPC-2581 (DPMX)** is a design→manufacturing XML file format (BOM, netlist, stackup, component placement) — a *product-model* data format, not a runtime config-sync protocol. It's referenced *inside* CFX as a possible `RecipeData` MimeType, and CFX v1.4 improved "utilization of IPC-2581 data." Not itself a machine↔MES sync channel.
- **MTConnect** is a read-mostly (HTTP/XML, agent-pull) machine-tool telemetry standard (CNC-oriented); not an inspection-config or bidirectional recipe channel.

## 2. Versioning & directionality — summary
| Standard | Direction | Versioning representation |
|---|---|---|
| IPC-CFX | Bidirectional (push `UpdateRecipe` + pull `GetRecipe` + activate + machine→MES `RecipeModified`) | Single optional free-text `Revision` string; no lineage/DAG. `RecipeModified` event = audit metadata (ModifiedBy/Reason/Notes/WorkOrderIdentifier), not content/diff |
| OPC UA MV | Bidirectional (`GenerateFileForRead`/`ForWrite`) | ExternalId + InternalId (InternalId may be a content hash = binary identity) |
| Hermes | Horizontal handoff only | n/a (not config) |
| SEMI E139/RaP | Bidirectional FICS↔equipment (SECS-II/SOAP) | PDE-based; semiconductor only |

## 3. Drift / conflict / governance (medium confidence)
No standard *mandates* a conflict-resolution or optimistic-lock discipline — that is left to the MES implementation. CFX gives the raw materials for a "golden vs reported" model: MES pushes via `UpdateRecipeRequest`, the machine announces edits via `RecipeModified` (who/why/version), and MES reconciles. This is exactly the **desired-vs-reported drift** pattern. Governance of *approved* limits (who may change LSL/USL, and when) is an MES/quality-system concern, not a standardized field. → Our server's model (integer version + atomic bump, last-write-wins with an opt-in `expectedUpdatedAt` optimistic lock, and a threshold-governance gate that blocks limit overwrites on non-development products) is *more* disciplined than any of these standards require.

## 4. Adoption in SMT/electronics AOI
- **Saki** 3Si SPI + 3Di AOI: IPC-CFX certified, on the IPC-CFX QPL (2021). [sakicorp.com; automation.com; aei.dempa.net]
- **IPC APEX EXPO 2019** joint Hermes+CFX live line included **Koh Young (post-reflow AOI)**, **Test Research Inc/TRI (AOX/X-ray)**, **Saki (SPI)** — three inspection vendors running both standards on one line. [the-hermes-standard.info; Electronic Design; electronics.org]
- General pattern: AOI/SPI vendors adopt **CFX** for machine↔MES messaging and **Hermes** for board handoff; there is no broad AOI adoption of OPC UA Machine Vision or SECS/GEM E139 in SMT.

## 5. Recommendations for the ST4I config-sync design
1. **Keep our rich internal schema** (measurement points + full spec + per-point/reference images + integer `pointsConfigVersion`, 2-way, governed). No standard offers a schema to adopt; a well-designed proprietary one is the right call and already exceeds the standards' content model.
2. **Model the envelope on CFX** for future interoperability: expose each product config as a CFX-Recipe-shaped object — `Name` = productModelCode, `Revision` = our version as a string, and (optionally) a `RecipeData` blob with a self-describing MimeType (e.g. `application/vnd.st4i.points+json`). Support the Update(push)/Get(pull)/Activate/Modified verbs conceptually — we already implement pull/push/version/history.
3. **Adopt a content hash as binary identity** (like OPC UA `InternalId`): we already compute a sha256 checksum — surface it as the drift key, matching CFX's checksum-first drift comparison and OPC UA's InternalId hash.
4. **Emit a RecipeModified-equivalent audit event** (who/version/reason/notes) on every push — matches CFX `RecipeModified` and good change-control; we already log sync history.
5. **Align measurement field names/units with CFX's `InspectionMeasurementTarget`** (ExpectedValue / MinimumAcceptableValue / MaximumAcceptableValue + units) so a future CFX bridge is a mapping, not a redesign. Our nominal/LSL/USL map 1:1.
6. **Reference images**: no standard carries golden/reference images in the recipe (CFX carries only *defect* images in results). Our `referenceImageUrl` (base64 or URL) is a sensible proprietary extension — keep it as a blob reference with a hash for dedup (we already do).
7. **Post-exhibition interop path**: a CFX (or OPC UA MV) *connector* that maps our internal config ↔ the standard's recipe envelope is the realistic bridge to third-party lines — align now on version/identity/audit semantics, defer the wire connector.
